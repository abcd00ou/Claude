## Problem Statement

영업·마케팅 조직원은 매일 실적 조회, 회의실 예약, 그 밖의 사내 시스템 정보 조회를 한다. 정보가 없는 것이 아니라 시스템마다 따로 들어가 메뉴를 타고 내려가야 하는 것이 불편이다. 처음 구상은 "마켓에서 기능을 가져와 커스터마이징하는 위젯"이었지만, 세션에서 좁힌 실제 제품은 **흩어진 사내 시스템을 PC 한 곳에서 단축키로 부르는 창구**다. 마켓은 그 위에 나중에 얹는 층이다.

## Demand Evidence

아직 없다. 제안자의 가설이다. 조직원의 요청, 임시방편 도구, 스폰서 지시 중 확인된 것은 없다. 이 문서의 가장 큰 위험이며, 아래 The Assignment가 이를 메우는 첫 행동이다.

## Status Quo

- 실적 조회: 실적 시스템에 로그인해 화면에서 확인한다. 매일 반복한다.
- 회의실 예약: 예약 시스템에 로그인해 빈 방을 찾아 예약한다.
- 그 밖의 조회: 시스템별로 따로 들어간다.
- 소요 시간과 클릭 수는 측정된 적이 없다. 기존 `dashboard/app.py`가 있어도 위젯이 필요한 이유는 이 측정으로 증명해야 한다.

## Target User & Narrowest Wedge

- 대상: 영업·마케팅 한 팀(10명 안팎). 특정 인물은 아직 지목되지 않았다.
- 첫 버전의 기능은 두 개뿐이다.
  1. 실적 조회 (읽기)
  2. 회의실 예약 (쓰기, 실행형)
- 조회 하나와 실행 하나라서 커넥터 구조의 읽기·쓰기 양쪽을 모두 검증한다.

## Constraints

- 두 시스템 모두 공식 API가 있다 (제안자 확인. 문서와 인증 방식은 미확인).
- 사내 PC에 데스크톱 앱을 설치하려면 IT 승인, 서명, 업데이트 경로가 필요하다.
- 조회 범위는 사용자 본인 권한을 넘지 않는다.
- 사용자가 올린 임의 코드를 PC에서 실행하지 않는다.

## Premises

세션에서 모두 동의했다.

1. 첫 버전은 마켓이 아니라 커넥터 2개다. 마켓은 서버의 목록 파일 하나로 시작하고, 가게 화면은 상품이 5개를 넘을 때 만든다.
2. 경쟁자는 기존 시스템 화면과 즐겨찾기다. 같은 일을 확실히 빨리 끝내지 못하면 실패다.
3. "내가 원하는 기능 추가"는 v1에서 설정 수준까지다 (카드 고정, 기능 켜고 끄기, 저장한 명령).
4. PC 클라이언트는 얇게 두고, 사내 API 호출은 전부 우리 서버가 대리한다. 인증은 사내 SSO.
5. 한 팀에 먼저 배포해 사용 횟수를 측정한 뒤 넓힌다.
6. 설치·업데이트 경로를 설계에 포함한다.

## Approaches Considered

### Approach A: 설치 없는 웹앱
링크 하나로 배포되지만 전역 단축키와 화면 상주가 안 되어 즐겨찾기와 차이가 작다. 전제 2를 만족하지 못해 탈락. IT가 설치를 막을 때의 대체안으로 남긴다.

### Approach B: 상주형 커맨드바 + 커넥터 게이트웨이 (선택)
아래 Recommended Approach.

### Approach C: 사내 메신저 봇
설치가 없지만 화면 표현이 메신저에 묶이고 "내 PC의 위젯" 구상과 다른 제품이 되어 탈락. 알림 통로로는 나중에 같은 서버에 붙일 수 있다.

### 구성

```
[PC 클라이언트: 트레이 상주 앱]
   단축키 입력창 · 카드 렌더러 · 고정 카드 · 설정(기능 목록)
        │  HTTPS (SSO 토큰)
        ▼
[게이트웨이 서버]
   /catalog   사용자에게 허용된 커넥터 목록
   /command   입력 문장 → 커넥터·동작·인자 결정 → 카드 데이터
   /actions   쓰기 동작 실행 (사용자 확인 후에만)
   /pinned    고정 카드 갱신
   감사 로그 · 권한 확인 · 응답 캐시
        │
        ├─ 실적 커넥터 ──▶ 실적 시스템 API
        └─ 회의실 커넥터 ─▶ 회의실 예약 API
```

### 결정 사항

- **클라이언트는 화면만 그린다.** 카드의 모양은 서버가 내려주는 정의(제목, 큰 숫자, 목록, 버튼)를 따른다. 새 커넥터는 서버 배포만으로 모든 PC에 나타난다. 이유: 클라이언트를 다시 배포하지 않고 기능을 늘리기 위해서다.
- **커넥터는 서버 안의 모듈이다.** 커넥터 하나는 설명 파일(이름, 버전, 대상 조직, 처리하는 명령 예시, 동작별 읽기/쓰기 구분)과 사내 API 호출 코드로 이뤄진다. 이유: 임의 코드가 PC에서 돌지 않아 보안 설명이 단순하다.
- **카탈로그는 서버의 목록 파일 하나다.** 커넥터 설명 파일들을 모은 것이며 Git으로 관리하고 리뷰를 거쳐 등록한다. 이유: 마켓의 본질은 유통이 아니라 "무엇을 누구에게 허용하는가"다.
- **v1 명령 해석은 규칙 기반이다.** 커넥터가 2개라 키워드와 날짜·시간·인원 추출만으로 충분하다. LLM 해석은 커넥터가 늘고 사내 데이터 반출 정책이 확인된 뒤에 넣는다.
- **쓰기 동작은 버튼을 눌러야 실행된다.** 입력만으로 예약하지 않는다. 완료 카드에 취소 버튼을 둔다. 같은 요청이 두 번 와도 예약이 두 번 되지 않도록 요청마다 고유 키를 붙인다.
- **장애 때는 마지막 성공 값과 시각을 보여준다.** 빈 화면이나 오류만 띄우지 않는다.
- **모든 호출을 감사 로그에 남긴다.** 누가, 언제, 어떤 커넥터의 어떤 동작을 불렀는지 기록한다. 사용 횟수 측정도 이 로그로 한다.
- **기술 선택(제안, IT 확인 필요):** 서버는 Python FastAPI (레포의 기존 코드가 Python). 클라이언트는 Tauri 같은 가벼운 웹뷰 기반 데스크톱 틀. 사내 PC의 OS와 웹뷰 정책을 확인한 뒤 확정한다.

### 비주얼 방향

시안: `docs/designs/sales-widget-commandbar-mockup-light.png`, `sales-widget-commandbar-mockup-dark.png` (원본 `sales-widget-commandbar-mockup.html`)

"쓰고 싶어지는 겉모습"은 채택 수단이다. 사내 도구처럼 보이면 열지 않는다.

- **유리 패널.** 입력창과 고정 카드는 뒤 화면이 비치는 반투명 패널이다. 업무 화면을 가리지 않고 그 위에 떠 있는 느낌을 준다. 모서리 반경은 패널 26px, 카드 20px, 버튼 14px.
- **숫자가 주인공.** 답은 화면에서 가장 큰 글자다 (실적 카드 숫자 68px, 굵기 800). 단위와 설명은 작고 흐리게 둔다.
- **강조색은 하나.** 블루(#3B82F6)에서 바이올렛(#8B5CF6)으로 가는 그라데이션을 진행 막대, 선택된 항목, 트레이 아이콘에만 쓴다. 성공은 초록, 나머지는 무채색이다. 회사 브랜드 색이 정해져 있으면 이 한 곳만 바꾼다.
- **라이트와 다크.** PC의 테마 설정을 따른다.
- **글꼴.** Pretendard (한글·숫자 모두). 숫자는 자간을 좁혀 덩어리로 보이게 한다.
- **움직임.** 패널은 0.18초 동안 살짝 커지며 나타난다. 실적 숫자는 0에서 값까지 0.4초 동안 올라간다. 예약 완료는 버튼이 체크 표시로 바뀌며 카드가 옆에서 밀려 들어온다. PC의 "애니메이션 줄이기" 설정이 켜져 있으면 모두 끈다.
- **키보드 우선.** 모든 동작에 단축키를 표시한다. 마우스 없이 입력, 선택, 실행, 닫기가 끝난다.
- **입력 해석을 보여준다.** "내일 2시 6인 회의실"을 날짜, 시간, 인원 칩으로 풀어 보여 주어 잘못 이해했을 때 바로 알 수 있게 한다.

### 범위 밖 (v1)

마켓 가게 화면, 사용자가 만든 커넥터 업로드, LLM 자연어 해석, 알림형 기능(시장 가격 급변 등), 메신저 연동.

## Open Questions

1. 두 시스템 API의 인증 방식: 사용자 토큰을 넘겨받는가, 서비스 계정으로 부르고 사용자 ID로 걸러내는가.
2. 사내 PC에 데스크톱 앱 설치가 허용되는가. 허용된다면 배포 도구와 코드 서명 절차는 무엇인가.
3. 사내 SSO의 규격(OIDC, SAML 등)과 데스크톱 앱 로그인 허용 여부.
4. 실적 데이터의 갱신 주기. 캐시를 몇 분까지 둘 수 있는가.
5. 프로젝트의 주인과 스폰서가 누구인가. 제안자가 자리를 옮겨도 살아남는가.
6. 세 번째 커넥터 후보. 레포의 `marketing/crawling_prices.py`, `market_intel.py` 데이터를 알림형 카드로 올리는 안이 유력하다.

## Success Criteria

제안 목표이며 The Assignment의 실측값으로 조정한다.

- 실적 조회: 단축키부터 숫자 확인까지 5초 이내 (기존 방식 실측값과 비교).
- 회의실 예약: 입력부터 예약 완료까지 15초 이내.
- 시범 팀에서 4주차에 주 4일 이상 쓰는 사람이 60% 이상.
- 게이트웨이 응답 시간 95번째 백분위 2초 이내.
- 본인 권한 밖의 데이터가 조회되는 사례 0건.

## Distribution Plan

- 클라이언트: 서명한 설치 프로그램을 사내 소프트웨어 배포 도구로 내려보낸다. 앱이 시작할 때 서버에서 새 버전을 확인해 자동으로 갱신한다. Open Question 2가 풀려야 확정된다.
- 서버: 사내망의 서버 한 대에 컨테이너로 올린다. 저장소에 병합하면 자동으로 빌드하고 배포한다.
- 설치가 막히면 Approach A(웹앱)로 같은 서버를 쓴다.

## Dependencies

- IT 담당자 확인: API 문서와 권한 발급, SSO, 데스크톱 앱 설치 정책 (Open Questions 1~3).
- 시범 팀 한 곳과 팀장의 동의.
- 서버를 올릴 사내 인프라.

## The Assignment

이번 주 안에 영업·마케팅 조직원 3명 옆에 각각 20분씩 앉아서, 실적 조회와 회의실 예약을 평소대로 하는 모습을 말없이 지켜본다. 휴대폰 초시계로 걸린 시간을 재고 클릭 수를 센다. 끝난 뒤 한 가지만 묻는다. "어제 사내 시스템에 들어가서 찾아본 것 세 가지가 뭐였어요?"

- 실적 조회가 이미 10초 안에 끝난다면 첫 커넥터를 바꿔야 한다.
- 세 사람의 "어제 찾아본 것"에 공통으로 나오는 항목이 세 번째 커넥터다.
- 이 숫자가 Success Criteria의 기준값이 되고, 스폰서를 설득하는 첫 자료가 된다.

## What I noticed about how you think

- "AX의 관점에서 조회같은것의 편의성밖에 생각안되는데"라고 먼저 말했다. 아이디어의 약한 곳을 스스로 짚은 것이고, 그 덕분에 조회형에서 실행형으로 방향을 옮길 수 있었다.
- 첫 기능 유형을 고를 때 추천(알림형)을 따르지 않고 "실행형"을 골랐다. 만들기 쉬운 쪽보다 일을 줄여 주는 쪽을 택한 판단이다.
- "토스의 인앱토스 처럼"이라는 비유로 시작했지만, 마켓 화면을 뒤로 미루는 전제에 바로 동의했다. 구상에 대한 애착보다 쓰이는 것을 우선했다.
- 수요 증거를 묻자 "아직 증거 없음, 내 가설"을 골랐다. 그 솔직함이 이 문서에서 가장 쓸모 있는 입력이었다.
